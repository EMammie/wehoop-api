### `game_changes` append-only trigger (new in fa47529)

Command:
`docker exec supabase_db_wehoop-api psql -U postgres -d postgres -c "update public.game_changes set body='{}' where false;"`
Output:
```
UPDATE 0
exit=0
```
(A no-op: with zero matching rows a row-level BEFORE trigger never fires, so this is only a syntax/permission sanity check, not a demonstration.)

Trigger present on HEAD's schema:
```
          tgname          | tgenabled |  pg_get_triggerdef
 game_changes_append_only | O         | CREATE TRIGGER game_changes_append_only BEFORE DELETE OR UPDATE ON public.game_changes FOR EACH ROW EXECUTE FUNCTION game_changes_append_only()
```

The real demonstration is the integration test **`game_changes rejects updates and deletes above retained_from_seq, allows deletes below`** (`test/integration/schema.test.ts:119`), which passed above in `test:int` (16/16). It inserts a game with seqs 1–3, asserts `update … seq = 1` rejects with `/append-only/`, asserts `delete … seq = 1` rejects with `/cannot be deleted/`, then sets `retained_from_seq = 2` and shows the `seq = 1` delete now succeeds leaving 2 rows — all inside a rolled-back transaction. Covered by invariant `game_changes_has_append_only_trigger expect 1 actual 1 PASS`.

Result: PASS (by test + invariant; the ad-hoc `where false` update is a no-op by design).
