## Observations (not acceptance rows; for the implementer)

1. **Local Realtime rate limit at `--pace 0` with a subscriber attached.** The first Run C (db reset #4, game `052d9c61-8847-47c5-9d6d-e2971bb4b640`, `--pace 0`) hit `HTTP 429 {"message":"You have exceeded your rate limit"}` from the local Realtime broadcast endpoint after seq 344 (`ERROR: outbox publish failed … count: 4`), the channel head was skipped with backoff, the pulse publish also got 429 (`WARN: pulse publish failed (harmless)`), and the worker exited 0 with `drained: published 0, skippedChannels 2` leaving `675|344|331` (total|published|unpublished, `attempts 1`, `dead 0`). Both subscribers then sat at seq 344 with no pulse to trigger catch-up and no publisher running. The run was abandoned and redone at `--pace 200`, which produced no 429 (`WARN=0 ERROR=0`). `supabase/config.toml` sets no `[realtime]` rate limit (defaults). Nothing was dead-lettered, and a later worker start would have drained the rows, but a worker that exits 0 with a skipped channel and a failed closing pulse leaves clients without a trigger until something else publishes. Same class of issue as the 429 noted in the superseded evidence.
2. **`GET /v1/games/:id/changes` returned HTTP 500 from an API process that outlived a `supabase db reset`.** The API started at 17:09:41Z (db reset #4) kept running through db reset #5 (17:12:57Z). Afterwards `/health` and `/snapshot` were 200 but every `/changes` request for Run C's game was `500 {"error":"internal"}` with `ZodError … "Invalid discriminator value. Expected 'event_insert' | … " path ["type"]` thrown from `gameChangeFromRow` (`src/model/game-change.ts:138`) via `loadChanges` (`src/api/routes/changes.ts:70`). The same rows decoded fine from a fresh process (`loadChanges` repro script: `parse OK` for seq 1–3, `loadChanges OK n= 2`), and after restarting the API every page was 200 (Equal shapes row). `public.game_changes.change_type` is a user-defined enum (`pg_type.typtype = e`, OID 18632 in that database; the OID changes on every reset). Hypothesis, not proven: postgres.js caches the enum's OID → parser per pool, and after the reset the new OID is unknown, so `changeType` arrives unparsed/undefined and the discriminated union rejects it. In production a running API never sees a schema drop, but a pooled client that cannot survive a type-OID change is worth a note; the Run C `receivedEqualsApi: null` in the Contiguity row is this issue.
3. **No-regression re-run appends `stats_team` changes.** See that row: rule 3 applies stats by hash regardless of generation, so a new generation replaying older post-phase summaries over a finished game writes 2 + 2 `stats_team` changes (older stats, then back). Final state is unchanged but the plan's "0 new changes" is not literally met; either the plan text or the stats precedence (e.g. `observedAt`/`updated` on stats) needs a decision.
4. **`watch_run_id` after a full re-run** advances once the new generation reaches post-phase documents (§4), so §8's "watch_run_id did not advance" holds for the 140 regressing batches only (each `stored.watchRunId = 1`), not for the run as a whole (1 → 2).
5. **`--until closed` stops at document 156**, so the closed summary and boxscore (157–158) are never applied; the final team stats come from document 153 (`complete`). `deleted_events = 2` because 3 of the 5 markers in the closed pbp name events that the sampled documents never inserted.
