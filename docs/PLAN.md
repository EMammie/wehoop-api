# wehoop-api: women's basketball stats backend (rev 4.5)

## Context

Goal: a "Real"-style live stats app for women's basketball (WNBA, NCAA Women's, Unrivaled) on Sportradar data. The existing iOS app **Wehoop** (`~/Desktop/Development/Wehoop/Wehoop`) calls Sportradar Unrivaled directly from the phone, which Sportradar's terms forbid and which cannot scale past a trial key. It has no WNBA/NCAAWB code, no play-by-play, no storage. This plan builds the backend, with Claude Code agents doing implement → review → validate → devlog per milestone, documented for social media.

Decisions made with the user:
- New public repo `~/Projects/wehoop-api`. Node 22 + TypeScript.
- Persistent Node worker on **Fly.io** (ingestion) + **Supabase** (Postgres, Realtime Broadcast, Auth). Live delivery behind a `LiveTransport` interface so custom SSE can replace Broadcast if measurements justify it. Local dev via Supabase CLI.
- All three leagues via adapters over one shared model; prove one full path (ingest → store → broadcast → client) on one recorded game first, **including dedupe, corrections, and crash recovery**, because those determine the schema.
- Canonical player identity: `players` + `player_external_ids(provider, league, external_id)`. Verified: Unrivaled player IDs are a separate ID space; Unrivaled Player Profile `references[]` (`scope`, `id_type`, `source_id`) links to WNBA/NCAAW IDs.
- **Phase 0 needs no trial key.** Sportradar Simulations (`playback.sportradar.com`) list recordings via GraphQL, need no auth, replay WNBA/NCAAWB REST feeds at natural pacing. Push replay exists but is rolling out; availability is per recording. Trial key requested when live-validation tooling (M3) is ready. Trial quotas are **per API product** (default 1,000 / rolling 30 days, 1 QPS), read from the console, not assumed.
- Agents: `.claude/agents/` subagents + slash-command skills first; GitHub Action PR review and Buffer posting added after the local loop works. Validators produce evidence, not "tests pass".
- Devlog: `devlog/NN-slug.md` per milestone + Buffer Idea draft (gated) + public repo with tags on validated merge commits.

Rev 2 incorporates the user's review: separate current plays from the change stream, allocate sequences only for real changes, fix the reconnect contract, private channels with receive-only authorization, budget-aware trial mode, outbox/worker recovery hardening, resilience moved into M1, hosted review out of M0, OOT season type, season-stat tables, `clock_running`, 120–150 h range.
Rev 3 adds: an explicit freshness/reconciliation policy (hash alone cannot order updates), durable vs observation writes, a `pulse` message carrying `latestSeq` so a missing final change is detectable, paginated `/changes`, one canonical `GameChange` schema shared by Broadcast and REST, and stricter evidence (joins, guest-session auth test, crash points around commit/publish).
Rev 4 → 4.2 (post-M0 review, 2026-10-12, two reviewer passes): replaces the monotonic basketball-progress key with a **run-generation freshness policy** (halftime no longer outranks the second half; clock corrections and explicit deletions are accepted; replay restarts and stale in-flight requests are rejected; game-level fields follow the newest observation), and makes outbox routing fields **derived from the change row by constraint** (composite FK + generated channel).
Rev 4.3 (M1 corrective pass, 2026-10-14, user + external review of PR #3): ratifies the three M1 contract questions (generation opening moves into `freshness.ts` as rule 2(d), which positions a lower score by the clock and defines how ambiguous summary-only observations are reconciled; every id inside a `LiveEvent` body is named `provider…Id`; `lineup_change` carries the reported on-court set), closes five correctness holes (unknown status, deletion revision, revision-only updates, omitted metadata, outbox head starvation), implements `pnpm release:tag`, and requires a committed, reproducible replay fixture behind every replay evidence row.
Rev 4.4 (M2 corrective pass, 2026-10-15, user review of PR #4): ratifies the M2 contract changes (`stats_team` / `stats_player` bodies and hashes are provider-keyed; `season_type` gains `CC`, the recorded WNBA value; an identity merge keeps the oldest row and tombstones the loser) and closes the identity-collision hole: `game_player_stats` is keyed on `(game_id, provider_player_id)` so a merge repoints and never deletes a row (a connected client and a fresh snapshot agree without any durable change), the order-dependent in-batch duplicate guard is gone, every automatic merge records its trigger and the content of anything it dropped in `ingest.player_merges`, ambiguous references are held in `ingest.player_merge_holds` instead of merged, and `player_team_seasons` is classified as roster data with named writers.
Rev 4.5 (M2 third corrective pass, 2026-10-16, owner decision after PR #4 review): a profile whose ids resolve to rows that contradict each other is **skipped on the reference path too**, not landed on the oldest candidate by an evidence-free tie-break (`conflicting_profiles` hold naming every row involved, `playerId: null`, nothing else written, the same as the own-id path); every hold **preserves the parsed document** (`player_merge_holds.document`, `document_observed_at`, `document_updated_at`, refreshed by a repeated document while the open hold stays single) so the held backlog is replayable through the normal path (`replayHeldDocument`) without a provider refetch. Checkpoint: M3 assesses the coverage impact of held profiles on the live run; before M5 beta the owner decides whether provisional profiles are needed (deferred-work note under §7).

Access control:
- `ingest` schema: `revoke all from anon, authenticated`; not in PostgREST `exposed_schemas`.
- `public` tables: RLS enabled, `select` policy for `anon` and `authenticated`; no insert/update/delete policies for clients.
- All views `with (security_invoker = true)`. No view may be used to "hide" a column; sensitive data lives in `ingest`.
- Realtime: `realtime.messages` RLS policy grants `select` (receive) to `anon`/`authenticated` on topics matching `game:%` and `league:%`; **no insert policy for clients**, so only the service-role publisher can send. Channels are `private: true`. iOS uses Supabase anonymous sign-in (guest session, no sign-up) so `setAuth` has a JWT.
- Test (M1): a client with the anon key attempts to broadcast a `status` message on `game:{id}`; assert rejection and that `bin/subscribe` never receives it.

League quirks: `games.coverage` drives watcher cadence and which change types NCAAWB extended-boxscore games emit (status/score/period only). Unrivaled Elam: `game_periods.type='elam'`, `elam_target_score`, clock null, `clock_running=false`. Unrivaled OOT games attach to `tournaments` and come from the Tournament Schedule feed, not the season schedule. `clock_extra` holds the two Unrivaled-only clock fields until a real fixture fixes the names.

## 3. Live event and change model

`src/model/live-event.ts` — body variants (discriminated on `type`): `tip_off, shot{made,points,shotType,providerAssistId?,providerBlockId?,location?,description}, free_throw{made,attempt,of}, rebound{kind}, turnover{kind,providerStealId?}, foul{kind,providerDrawnById?}, timeout{kind}, lineup_change{providerOnCourtPlayerIds[]}, period_start, period_end, game_status{status}, elam_target_set{target}, awarded_point{...} (Unrivaled 1v1), review{outcome?}, other{providerEventType,description?}`. Each body carries `period{number,type,sequence}, clock, clockDecimal?, wallClock, score{home,away}, providerTeamId?, providerPlayerId?, providerPossessionTeamId?`.
**Every id inside a body is a provider id and is named `provider…Id`** (`providerTeamId`, `providerPlayerId`, `providerPossessionTeamId`, `providerAssistId`, `providerBlockId`, `providerStealId`, `providerDrawnById`, `providerOnCourtPlayerIds`). Canonical uuids (`teams.id`, `players.id`) are columns on `play_events` resolved by `identity.ts` from M2; they never enter the body or the content hash, so an identity merge never rewrites history (ratified 2026-10-14). `lineup_change` carries the lineup as the provider reports it, the full on-court set after the change; in/out are derived by the client from consecutive lineups, because deriving them in the normalizer would make a pure function stateful.

`content_hash` = sha256 of the canonical JSON of the **body only** (no seq, no ingestion timestamps, no provider `updated` field). Hash equality means "unchanged"; hash inequality alone never decides direction. Direction comes from the freshness policy in §4.

**One canonical `GameChange` schema** (Zod, in `model/game-change.ts`; the only shape Broadcast, `/changes`, `game_changes`, and the Swift mirror use):
```ts
{ v: 1, id: uuid, gameId, seq, ts: iso, type: 'event_insert'|'event_update'|'event_delete'|'status'|'period'|'stats_team'|'stats_player', providerEventId?: string, body }
```
Stored as columns + `body jsonb` in `game_changes`; the envelope is rebuilt from columns on read, so equality is tested on **decoded** `GameChange` objects (deep-equal after Zod parse), never on JSON bytes.
- `event_update`: full replacement body. `event_delete`: body `{providerEventId}`.
- `status`: `{status, score, period}` — durable changes own score, period, and status.
- **Clock is never a durable change.** During live play the worker sends a `pulse` message every 10 s (and once on close) directly to the transport, never to `game_changes`:
  `{ v:1, type:'pulse', gameId, latestSeq, status, clock, clockDecimal?, clockRunning: true|false|null, clockAsOf, observedAt }`.
  Client rules: ignore a pulse whose `observedAt` ≤ the last applied pulse; if `latestSeq` > last applied durable seq, fetch `/changes`; count down only when `clockRunning === true`, anchored to `clockAsOf`; when `null`, display the last observed clock frozen. Pulses never touch score or period.

Unknown provider types → `other`, never throw. One shared Sportradar basketball normalizer; adapters override league quirks only. `pnpm gen:swift` emits `LiveEvent.swift` + `GameChange.swift` into Wehoop at M5.

## 4. Ingestion

- **`LeagueAdapter`**: `capabilities{pushClock,pushEvents,pushStats,coverageFor}`, `schedule/summary/boxscore/pbp/teamProfile/playerProfile/standings/hierarchy/changes/seasonalStats/tournamentSchedule`, `normalizePbp()`, `openPush?()`. One `SportradarHttp` with `UrlResolver` = `ProdUrlResolver(product, access, key)` | `SimulationUrlResolver(recordingId, sessionId)`. `bin/sim.ts`: GraphQL `recordings(league:)`, `createSession`, prints per-recording feed availability.
- **Freshness policy** (`ingest/freshness.ts`). The M0 review showed that a monotonic "basketball progress" score cannot order observations: `halftime` would outrank the second half, a clock restored after a review lowers the score, an explicit deletion lowers the event count, and equal-progress payload differences prove nothing about direction. Freshness is therefore decided by **watch generation** and **per-entity precedence**, never by one scalar.
  Every normalized batch carries an `Observation`: `{source: push|rest|simulation|fixture, runId, watchId | null, observedAt, providerUpdatedAt?, isComplete, gameView?}`.
  - `runId` = the `ingest.ingestion_runs.id` that produced the batch. `watchId` = the **watch generation**: the root `watch_game`/`replay` run for this game; `push_stream` and `backfill` sub-runs (REST reconciliation after a stream drop is a `backfill`) carry `parent_run_id` and inherit the root's id: `watchId = coalesce(parent_run_id, id)`, depth 1, enforced by `check ((kind in ('push_stream','backfill')) = (parent_run_id is not null))` so a generation cannot be forged any more than outbox routing can. Several sub-runs of one generation touch a game concurrently without fighting. `games.watch_run_id` records the generation that last wrote. Schedule polls and `changes(date)` runs have `watchId = null`: they are **generation-less**, skip rules 1–2, never advance the generation, and are limited to rule 3 with one extra restriction: a generation-less batch may write `gameView` only while the stored phase is pre or `last_seq = 0`, and it never writes score, period, clock, or `clock_running`. It may always fix `scheduled_at`, venue, broadcasts, and coverage. During a live or finished game its lagging `gameView` (the schedule feed is cached far longer than pbp) is logged `superseded_observation`, so a poll can never emit a regressive `status` change or silence a watcher.
  - `observedAt` = REST/sim: the **request start** time (the document is at least that old); push: message receipt time; fixture: test-supplied. Our clock, never the provider's.
  - `isComplete` = the batch is a whole pbp document (REST/sim pbp, backfill) as opposed to a single push event or a summary without events. `gameView` = the batch's own game-level state (status, period sequence, score, clock) when the payload carries one; single push events have none.
  Rules, applied in order inside the `applyChanges` transaction:
  1. **Older generation → stale** (`reason=older_run`). `watchId < games.watch_run_id`: a batch from a watcher that has since been replaced (restart, lock loss, operator restart). Nothing is written except one `stale_observations` row.
  2. **New generation → non-regression gate** (`watchId > watch_run_id`, or `watch_run_id is null and last_seq > 0`, i.e. the game has durable state from an unknown generation). The batch is stale (`reason=run_regresses_state`) if any of: (a) `gameView` present and `phase(status)` lower than the stored phase, where `phase` is pre `{scheduled, created, time_tbd, if_necessary}` < live `{inprogress, halftime, delayed}` < post `{complete, closed, cancelled, postponed, unnecessary}`; post → pre is allowed only when `last_seq = 0` (a postponed game rescheduled before anything live was recorded); (b) `gameView` present, same phase, and `gameView.periodSequence < games.current_period_sequence` (the batch's game-level period, never an individual event's); (c) `isComplete` and the document's **newest event position** is behind the stored newest live event, where the stored side excludes events the incoming document lists in `deleted_events[]` (so a provider deleting the final play of a closed game does not poison later generations). Position = `(period_sequence, provider_sequence)` with nulls broken by `provider_number`, then `wall_clock`; an `isComplete` document whose events carry none of these is not gated by 2(c). 2(c) is a position comparison, not set containment: a replay restart is always behind, while a provider silently dropping one old event is not, so a single anomaly cannot poison every future generation. (d) **Summary-only score regression**: `gameView` present, the batch carries no events or deletion markers, same phase, same period sequence, and `gameView.score` lower than the stored score on either side. A lower score alone proves nothing, because a legitimate correction (a waved-off basket) lowers it too, so direction comes from the clock position inside the period. If both `gameView.clock` and the stored `games.clock` are known and the incoming clock shows **more** time remaining than stored, the observation sits earlier in the period than what is stored and is stale (`run_regresses_state`, detail `2d`); equal or less time remaining is a correction and is accepted. If either clock is unknown (Elam periods, feeds without a clock) the observation is **ambiguous**: logged `ambiguous_regression`, nothing written, generation not advanced. Reconciliation is explicit: the generation is accepted by its next batch that is not ambiguous (an event-bearing batch that passes 2(c), a `gameView` at or above the stored score, or a `gameView` whose clock positions it), **or** by a second ambiguous observation from the same generation with the same score and a later `observedAt`, provided every `ambiguous_regression` row for this game and generation carries that same score (read inside the transaction), which corroborates the lower score as a correction. A replay restarted inside the period keeps climbing, so it never corroborates itself; a real correction repeats. Rule 2(d) replaces M1's watcher-side "generation opened by an event-bearing batch" guard, which lived outside the transaction, dropped documents without a log row, and could not serve NCAAWB extended-boxscore games that never carry events. On acceptance `watch_run_id` advances **regardless of whether the game-level observation is written** (rule 3). This is what makes "replay restarted at 0–0" harmless. A worker that stops on `closed` still consumes the remaining documents of a replay file, and a live watcher fetches one final summary and boxscore after `closed`, so final stats are never left behind. A worker restart mid-game is a new generation whose first batch is at or ahead of stored state and passes; in push mode the first REST document after a restart may trail pushed state by a few seconds and be logged stale once, then the first accepted push event (non-complete, no `gameView`, so 2a–2c do not apply) advances the generation and later documents fall under rule 3. Three consecutive `run_regresses_state` rows for one game raise a metric/alert; the escape is `pnpm game rebuild`. Reversing a terminal status with live history is an operator action, never automatic.
  3. **Same generation (or generation-less) → per-entity precedence**, no batch-level staleness:
     - *Events*: if both sides carry provider `updated`, the newer wins and an older incoming event is ignored (counted, not logged as stale). A newer `updated` with an **identical body is a revision-only update**: `play_events.provider_updated_at` (and the raw copy) advance, no change row and no `seq` are produced; without this, revision 12 repeating revision 10's content would leave the row at 10 and a later, differing revision 11 would overwrite it. Equal or missing `updated` → compare `content_hash`, a differing body is a correction and is applied even when it lowers clock or score. A **deletion happens only on an explicit marker** (`deleted_events[]`, push `operation=delete`); absence from a document never deletes. The marker's own revision (`updated` on the `deleted_events[]` entry or on the push message) is persisted as `play_events.deleted_revision_at`; a marker whose revision is older than the stored event's `updated` is an **older deletion** and is ignored (counted); a marker without a revision is applied, because it is an explicit statement by a current document, and recorded with `deleted_revision_at = null`. A deleted event is reinstated only by an incoming `updated` newer than `coalesce(deleted_revision_at, provider_updated_at)`; when neither side carries a revision the deletion is sticky and `pnpm game rebuild` is the escape.
     - *Game-level fields* (status, score, period, clock, `clock_running`): written only when `gameView` is present and `observedAt > games.observed_at`; otherwise the batch's game-level view is **superseded** (`reason=superseded_observation`, logged, no game-level write) while its events are still reconciled per entity. This settles "delayed REST racing a newer push at equal progress": the REST request started before the push message arrived, so it cannot overwrite status or clock, but any event-level corrections it carries are honoured by `updated`.
     - *Stats* (`stats_team`, `stats_player`): per-entity **observation precedence**, like game-level fields. Each stats row carries `observed_at`; an incoming stats entity is applied only when the batch's `observedAt` is newer than the stored row's `observed_at` (or the row is new), and produces a change row only when its `content_hash` differs. Older observations are ignored (counted, not logged). Official corrections on `closed` games arrive later and therefore always apply; a replay restarted after the final whistle re-presents older stats documents and must not oscillate (the M1 evidence at 631ff1c caught exactly this: a re-run wrote 4 `stats_team` changes, two regressions and two restorations).
     - *Omission is not change*: a document that omits `coverage`, `updated`, venue, or broadcasts leaves the stored value in place. The normalizer maps absence to `null` and the SQL `coalesce`s it; only a present value is a change. The normalizer never invents a value: an unknown provider `status` is reported on the batch (`unknownStatus`, logged with the raw string) and the stored status is kept, never mapped to `scheduled`.
  4. **Operator override**: `pnpm game rebuild --game <id>` clears state and replays from a chosen source for forensics. Never automatic.
  Feeds without usable timestamps (NCAAWB extended boxscore summaries, some sim recordings) work on rules 1–3 unchanged: they lack `updated`, so events fall to hash compare, and game-level fields follow `observedAt`. Elam periods have a null clock; no rule reads the clock.
  **Acceptance cases for `freshness.ts`** (unit tests with fixtures, re-proven in the M1 replay evidence): halftime → period 3 `inprogress` accepted; clock correction 5:00 → 5:30 inside one period accepted and observed; explicit deletion lowering the event count accepted as exactly one `event_delete`; absence of events without a marker never deletes; delayed REST (`observedAt` earlier than the stored push observation) → `superseded_observation`, no game-level write; replay restart from 0–0 as a new generation → `run_regresses_state`; in-flight batch from an older generation → `older_run`; worker restart mid-game as a new generation → accepted; a push sub-run and a backfill sub-run of the same generation interleave without either being marked stale; a generation-less schedule poll during a live game never advances `watch_run_id` and never overwrites a newer clock; a complete document missing one old event (not the newest) is not stale; a generation-less poll with a lagging score during a live game writes nothing game-level and logs `superseded_observation`; a new generation's first document that explicitly deletes the stored newest event is accepted and yields one `event_delete`; a new generation's summary-only document inside the stored period with a lower score and more time on the clock → `run_regresses_state` (2d, the stale summary after a restart); the same with the clock at or past the stored clock → accepted and written as a downward correction after a restart; the same with no clock on either side → `ambiguous_regression`, no write, `watch_run_id` unchanged; a repeated ambiguous observation with the same score and a later `observedAt` → accepted; an event-bearing batch after an ambiguous one advances the generation; an unknown provider status keeps the stored status and is reported, never `scheduled`; a deletion marker with a revision older than the stored event's `updated` is ignored; a deletion marker without a revision is applied and recorded with a null `deleted_revision_at`; an incoming event with a newer `updated` and an unchanged body advances the stored revision and produces no change; a document omitting `coverage` or `updated` keeps the stored values.
- **`applyChanges(gameId, normalized, observation)`** (`ingest/apply-changes.ts`), one transaction, two write categories:
  1. `SELECT … FROM games WHERE id=$1 FOR UPDATE` (serializes per game).
  2. Freshness gate, rules 1, 2(a), 2(b). Stale → one `stale_observations` row, commit, nothing else.
  3. Load current `play_events(provider_event_id, content_hash, deleted_at, provider_updated_at, period_sequence, provider_sequence)` for the game; then rule 2(c). Accepted new generation → `watch_run_id = watchId`.
  4. Diff into durable changes using rule 3 precedence: `event_insert`, `event_update` (hash differs and not older by `updated`), `event_delete` (explicit marker only, not yet deleted), `status`/`period` (only when this batch's `observedAt` is newest), `stats_*` via their own hashes.
  5. **Observation write (when `gameView` is present and this batch's `observedAt` is newest)**: `games.clock, clock_decimal, clock_running, clock_as_of, clock_extra, current_period_sequence, observed_at, observed_source, provider_updated_at`. No seq increment, no change row. Superseded batches skip this step and log `superseded_observation`; `watch_run_id` was already advanced in step 3.
  6. **Durable write (only if `n > 0`)**: `UPDATE games SET last_seq = last_seq + n RETURNING last_seq`; number changes `last_seq-n+1 … last_seq`; upsert `play_events` current state; insert `play_event_raw`; insert `game_changes` (with new `id`s); insert `broadcast_outbox` (`change_id` PK); `NOTIFY outbox`.
  `clock_running` derivation: WNBA push clock gives it directly; REST summaries give `true` when `status=inprogress` and the clock advanced between two observations, `false` at period end/timeouts when the feed says so, `null` otherwise.
  Guarantees by construction: applying the same normalized batch twice yields zero changes; an older generation never regresses state; within a run a correction is applied even when it lowers clock or event count, and appends exactly one change per changed entity; `seq` is gap-free.
- **Identity** (`ingest/identity.ts`, rev 4.5). One canonical `players` row, many `player_external_ids(provider, league, external_id)`. Game feeds create players (`source=game`); a profile owns its id (`profile`) and links its `references[]` (`reference`). A profile **resolves every id it carries before writing anything**: it lands on the row its own id resolves to (else the oldest row a reference resolves to, else a new row), merges every other row a reference resolves to, and links the ids nobody knew. **Merge rule**: survivor = oldest row (`created_at`, then id), loser gets `merged_into` (chains flattened to depth 1), external ids move, `play_events` / `game_player_stats` / `player_season_stats` are repointed by `apply-changes.ts` and `player_team_seasons` by `identity.ts`; `game_player_stats` is provider-keyed and never dropped; a season line or team season whose key the survivor already owns is dropped but its full content is persisted in `ingest.player_merges.conflicts` with the trigger (document + reference entry). Canonical uuids never enter bodies or hashes, so a merge rewrites no history and needs no durable change. **Only supported references are linked automatically**: a scope in the known league aliases (`WNBA`, `NCAAW`/`NCAAWB`, `UNRIVALED`) and an id type in `{league_profile, sport_profile, external}`. Anything ambiguous is **held** in `ingest.player_merge_holds`, never merged: unknown scope or id type; an id already stored under another id type; an id owned by a tombstone; and `conflicting_profiles`, when the two rows would give one person two profile-owned `league_profile` ids in one league or two different `sport_profile` ids (the provider contradicting itself). Sport-wide ids are compared **regardless of the league they are stored under** (a row stores a sport id under the league of the profile that carried it): two different sport ids on two rows are a conflict whichever leagues carried them, and one matching sport id across leagues links normally. The check runs on **both paths**, before anything is written: when a reference resolves to another row (the hold names every row involved: the home row, the rows owning the counter-claims, and that row, with the contradicting `{theirs, against: {claim, owner}}` pairs in `detail`) and when the document's **own id already resolves** to a row whose existing profile claims it would contradict (the hold names that row and carries the own id as its reference). **On either path the whole document is skipped** (rev 4.5): no id upgrade or link, no merge, no attribute overwrite, no seasons or season lines, `playerId: null`, exactly like a held own id; a conflicting document is never landed on a candidate by tie-break, because nothing in the data says which row it belongs to. Every hold keeps the parsed document (`player_merge_holds.document`) so it can be replayed through the same path once the contradiction is resolved. Two game-sourced ids of one league claimed by a profile do merge (that is the real-world duplicate-record case); the first of their league profiles then upgrades its id, the second is the own-id conflict above. Re-applying a document is a no-op: no second merge row, no second open hold (the stored body and `document_updated_at` refresh).
- **Rate/quota**: `RateLimiter` (1 s slots) wraps production calls; every call logs `provider_calls` with `product`. `QuotaGuard` reads `ingest.v_quota` per product and `ingest.product_quotas` (seeded from console limits; config override), refuses below reserve.
- **Trial mode** (`ingest/trial-mode.ts`, `MODE=trial`): no automatic discovery. Operator runs `pnpm trial plan --league ncaawb --date 2026-11-08` (1 schedule call) and `pnpm trial watch --game <id> --profile full|extended` which computes the call budget for that profile, writes a `budget_reservations` row, and refuses if `remaining - reserved < reserve`. Profiles: `full` = pbp every 30 s + boxscore every 5 min for ~2.5 h ≈ 330 calls; `extended` = summary every 60 s for 2.5 h + 1 boxscore at +120 min ≈ 150 calls; `lean-full` = pbp every 60 s ≈ 165 calls. Daily `changes(date)` is **off** in trial mode. A 1,000-call NCAAWB trial therefore covers roughly two full games plus one extended game plus discovery; this is stated in the M3 devlog honestly.
- **Production/simulation scheduler**: schedule for today+tomorrow per league at 06:00 + hourly in game windows; `changes(date)` every 30 min in season (production only). `GameWatcher` cadence by `(source, capabilities, coverage)`: sim = pbp/3 s; prod push = events+statistics (+clock WNBA) + REST pbp/5 min reconciliation.
- **Push client**: chunked fetch, newline split, Zod-parse (`heartbeat` | `{payload, metadata{operation,event_type}}`), 15 s no-bytes watchdog, jittered backoff 1–30 s, then `backfill(gameId)` = full REST pbp through `applyChanges`.
- **Worker lifecycle**: on start, open the **session-mode** connection, `pg_try_advisory_lock(hash('wehoop-worker'))`; exit if not acquired. If that connection drops, stop all watchers and exit (Fly restarts it). On start and every 30 s, drain the outbox regardless of `NOTIFY` (NOTIFY is a wake-up hint only).
- **Outbox publisher**: single publisher per process (the lock holder); per channel, publish in `seq` order. The drain first selects every channel's **head** (its lowest unpublished, non-dead `seq`) and keeps only channels whose head is publishable now (`next_attempt_at <= now()`); it then takes up to 200 rows across those channels **round-robin by position** (`row_number() over (partition by game_id order by seq)`, ordered by that rank, then channel) and publishes per channel the contiguous prefix from the head. The limit is applied **after** head exclusion, so a channel with a blocked head or a long backlog can never fill the batch and starve healthy channels (a stuck head blocks its channel, not the system). Publish is at-least-once: a crash after the HTTP send but before `published_at` is written re-sends the same `GameChange` with the same `id`; clients dedupe on `id`/`seq`. Retry with exponential `next_attempt_at`; after 10 attempts set `dead_at`. Recovery: `pnpm outbox requeue --channel game:<id>`; clients recover regardless via `/changes` because the durable stream is `game_changes`.
- **Pulse sender**: every 10 s per live game and once when status becomes `closed`, build `pulse` from `games` observation columns + `last_seq` and send directly through `LiveTransport` (not outbox). Loss is harmless; the next pulse supersedes.
- **Reconnect contract** (client; `bin/subscribe.ts` is the reference implementation and is tested):
  1. Subscribe to `game:{id}`; buffer incoming `GameChange` and `pulse` messages.
  2. `GET /v1/games/:id/snapshot` → `{state, seq}` from **one** `REPEATABLE READ` transaction.
  3. Apply buffered changes with `seq > snapshot.seq` in order, deduping on `id`; drop the rest.
  4. On gap (`msg.seq != last+1`) or on a `pulse` with `latestSeq > last`: page `GET /v1/games/:id/changes?after=last` until `hasMore=false`; if the response says `retainedFrom > last+1`, go to step 2.
  5. On reconnect, app foreground, or network change: go to step 4 (step 2 if the gap is large or unknown).
  6. When a change or pulse reports `status=closed`, fetch one final snapshot.
  Pulses update only clock display and trigger step 4; they never change score, period, or status.
